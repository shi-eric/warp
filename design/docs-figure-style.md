# Documentation Figure Style

**Status**: Proposed, 2026-10-31. Applies to figures added to the Sphinx site from the Distributed Computing
section onward. Existing figures are migrated when they are next touched.

## Motivation

The Sphinx site uses `nvidia_sphinx_theme`, which inherits `pydata_sphinx_theme` and offers a light and a dark
mode that the reader toggles in the header. The figures in `docs/img` predate that toggle: the tape graph comes
from Graphviz, the compiler pipeline from a drawing tool, the Jacobian plots from matplotlib, each a single file
with black text and no shared style. In dark mode the theme falls back to drawing a white box behind every untagged
image and applying a contrast filter, so the figures read as pasted in rather than part of the page.

The NVSHMEM documentation adds seven diagrams that explain processing elements, symmetric memory, halo exchange
and the backward pass. Their first hand-drawn drafts had labels that overflowed their boxes, arrows that crossed
text, odd curves and arrowheads out of scale with the drawing. A reviewer asked for figures that fit the theme in
both modes. That request needs rules for what a figure looks like and a production method that makes a set of
figures consistent and keeps them so when one changes.

## Requirements

| ID  | Requirement                                                                                      | Priority | Notes                                                                         |
| --- | ------------------------------------------------------------------------------------------------ | -------- | ----------------------------------------------------------------------------- |
| R1  | A figure renders correctly in both theme modes and follows the site's toggle, not the OS setting | Must     | The toggle sets `html[data-theme]`; it does not change `prefers-color-scheme` |
| R2  | Colors come from the theme's stylesheet                                                          | Must     | `nvidia-sphinx-theme.css`, plus pydata defaults the theme does not override   |
| R3  | Text fits its box with the fonts the browser actually uses for an image                          | Must     | An SVG in an `<img>` does not get the page's web fonts                        |
| R4  | Arrows never cross text; they are straight or orthogonal; arrowheads are proportional to strokes | Must     |                                                                               |
| R5  | Code in a figure is spelled as the reader types it                                               | Must     | `wp.nvshmem_put(...)`, never the bare library name                            |
| R6  | Figures are generated by a committed script with deterministic output                            | Must     | Hand-editing SVG is not a maintenance path                                    |
| R7  | No new documentation build dependency                                                            | Must     | No Graphviz or Mermaid at build time                                          |
| R8  | Every figure has alt text and a caption inside the image                                         | Should   | The file stands alone when copied out of the page                             |
| R9  | Existing figures migrate to the style when touched                                               | Could    | Not a project of its own                                                      |

**Non-goals**: screenshots and rendered example outputs under `docs/img/examples`, which are images rather than
diagrams; animated figures; plots produced by running code, such as the Jacobian visualizations, which may adopt
the palette but are not produced by the generator described here.

## Design

### Approach

Each figure ships as two SVG files, a light and a dark variant, generated from one layout by a committed Python
script. The page embeds both with the theme's `only-light` and `only-dark` image classes, so the toggle shows one
and hides the other together with its caption. The variants differ only in the colors substituted from two
palette tables taken from the theme's stylesheet.

Two facts about the browser decide this. An SVG referenced by an `<img>` tag is an isolated document: it cannot
read the page's CSS custom properties, so a single file cannot recolor itself when the theme changes. And the
theme's toggle writes a `data-theme` attribute on the `html` element; a `prefers-color-scheme` media query inside
the SVG would follow the operating system, not the toggle. The pair mechanism is pydata's documented answer to
both, and it keeps the `figure` directive with its alt text, width, caption and numbering.

### Palette

Values from `nvidia-sphinx-theme.css` and, for the border, from pydata's defaults, which the NVIDIA theme does
not override. A figure uses these roles and no other colors.

| Role                                                   | Light                                                        | Dark      | Theme variable                                      |
| ------------------------------------------------------ | ------------------------------------------------------------ | --------- | --------------------------------------------------- |
| Text                                                   | `#1a1a1a`                                                    | `#eeeeee` | `--pst-color-text-base`                             |
| Captions, secondary labels, dim arrows, dashed borders | `#666666`                                                    | `#999999` | `--pst-color-text-muted`                            |
| Panels and surfaces                                    | `#f7f7f7`                                                    | `#1a1a1a` | `--pst-color-surface`                               |
| Panel borders                                          | `#d1d5da`                                                    | `#48566b` | `--pst-color-border` (pydata default)               |
| Code labels, data-movement arrows, guides              | `#004831`                                                    | `#76b900` | `--pst-color-primary`, the page's inline-code color |
| Highlighted regions (shared data, symmetric arrays)    | `#76b900` at 22% (light) / 25% (dark) fill, `#76b900` stroke |           | `--nv-color-green`                                  |
| Waiting or blocked operations                          | `#b35c00`                                                    | `#f0a742` | amber, chosen for contrast on each background       |
| Barriers and synchronization points                    | `#999999`                                                    | `#777777` | neutral grey                                        |

The primary color switches between NVIDIA's dark green and NVIDIA green exactly as the page does for inline
code, so a code label in a figure matches the inline code around it. NVIDIA green on a white background has a
contrast ratio near 2.2:1 and is never used for text or thin lines in light mode; it appears there only as a
tinted fill with a stroke.

Backgrounds are transparent. The page's background shows through, and the figure needs no box.

### Typography

Text is set in the system fallbacks of the theme's font stacks, because an image does not receive the web fonts
the page loads:

- labels and captions: `Arial, Helvetica, sans-serif`
- code: `SFMono-Regular, Menlo, Consolas, monospace`

Sizes are given in a 640-unit-wide `viewBox` and scale with the content column. Title 13, labels 12, code 10.5
to 11, captions 10.5. A figure that needs smaller text than 10.5 units at 640 wide is too dense and is split.

Text is measured before its box is drawn: a per-character width table for the fallback fonts, with a margin of
at least 12 units on each side, decides the box width. Boxes are sized from text, never text squeezed into boxes.

### Geometry

- `viewBox` width 640 for standard figures and 800 for wide timelines; height as the content needs. Figures are
  embedded at 100% of the content column.
- Strokes: 1 for borders, 0.8 for dashed guides, 1.2 for secondary arrows, 1.6 for data-movement arrows.
- Arrows are straight, or orthogonal with at most two bends, and run through channels declared per figure:
  the gaps between panels, margins, or lanes reserved between rows of text. No arrow crosses text or enters a box
  except at its target edge.
- Arrowheads are one `<marker>` per arrow color, 6 by 6 units at stroke 1.6, about four times the stroke width.
- Related elements that share a position across panels (the same offset in every heap, the same step on every PE)
  are connected by dashed guides drawn behind the panels, so they show only in the gaps.
- Dashed borders mark regions that are not objects of their own, such as a heap inside a process.
- A one- or two-line caption in the muted color sits inside the figure at the bottom.
- Lane diagrams (streams, timelines) use one horizontal line per lane, labelled at the left margin, with
  operations as rounded rectangles on the lane and cross-lane dependencies as data-movement arrows.
- Ties that synchronize lanes without moving data are dashed lines in the muted color, stroke 1.2, dash `4 3`,
  checked against channels, text and boxes like arrows. An event tie has an arrowhead and runs from the lane of the
  stream that records the event to the lane of the stream that waits on it, through the gap between the kernels the
  event separates. A barrier tie joins the barrier operations of every PE and has no head, because a barrier holds
  each PE until all of them arrive.
- Operation widths come from their labels unless a shared time axis sets them, so they show order and overlap, not
  durations, and a lane diagram says so in its caption when a reader could compare lengths. Panels that share a
  time axis draw the same work at the same width.

### Code and names

A label that shows code shows what the reader types in a kernel or on the host, with the `wp.` prefix and Warp's
argument names. Library-level names (`nvshmem_put`, `cumodule_init`) appear only where the figure is about the
library layer itself, and then in the muted color.

### Files, naming and embedding

Figures live next to the section that uses them, as `docs/img/<section>/<stem>-light.svg` and
`docs/img/<section>/<stem>-dark.svg`, generated by `docs/img/<section>/generate.py`. The first section to adopt
this is `docs/img/distributed/`. When a second section needs figures, the shared parts of the generator (palette,
text measurement, markers, arrow routing) move to `docs/img/_lib/` and the per-section scripts import them.

A page embeds a figure twice:

```rst
.. figure:: /img/distributed/symmetric_heap-light.svg
    :class: only-light
    :alt: Three PEs with symmetric heaps; array u at the same offset on each; a put from PE 0 into u on PE 1.
    :width: 100%

    Processing elements and the symmetric heap

.. figure:: /img/distributed/symmetric_heap-dark.svg
    :class: only-dark
    :alt: Three PEs with symmetric heaps; array u at the same offset on each; a put from PE 0 into u on PE 1.
    :width: 100%

    Processing elements and the symmetric heap
```

The `:class:` option of the `figure` directive lands on the image element, which is what pydata's rules select;
the sibling `figcaption` is hidden by the same rules. Both variants carry the same alt text and caption. The RST
caption only names the figure, without restating the title; the SVG carries the title and the caption.

### The generator

- Python with the standard library only; it runs with `uv run docs/img/<section>/generate.py` and rewrites every
  variant of every figure in its section.
- Declarative layouts: a figure is a list of panels, boxes, labels, lanes, arrows and channels with positions in
  `viewBox` units. The script measures labels, sizes boxes, checks that each arrow stays inside its channel and
  that no box or label overlaps another, and refuses to emit a figure that violates a rule.
- Deterministic output: the same input produces byte-identical files, so a diff in a review shows real changes.
- A `--check` mode regenerates into memory and compares with the committed files, for use in a pre-commit hook or
  a documentation job later.

### Alternatives considered

- **Graphviz or Mermaid at build time.** Adds a documentation build dependency, and the output still does not
  follow the toggle without producing two variants. Rejected.
- **One theme-neutral SVG with the `dark-light` class.** Opts out of the white box, but any text color readable on
  both backgrounds is low-contrast on both. Rejected.
- **Inline SVG through `raw:: html`** using the theme's CSS variables. Follows the toggle with one file, but loses
  the `figure` directive, its alt text, width and caption handling, and the page-source copy. Rejected.
- **Hand-authored SVG in a drawing tool.** This is how the existing figures were made. Nobody can regenerate them,
  and a palette change means redrawing. Rejected for new figures.
- **Exporting PNG images.** Blurry at the content widths the theme uses on large displays, and no smaller to maintain.
  Rejected.

## Testing Strategy

- The generator runs twice and the outputs are byte-identical.
- The documentation build is warning-free with the figures embedded.
- The built HTML is checked once in a browser under both themes: the right variant shows, the caption switches
  with it, and no white box appears behind the figure.
- A review of each figure against the rules above: text inside boxes, arrows in channels, one marker style, the
  caption present, code spelled as the reader types it.
